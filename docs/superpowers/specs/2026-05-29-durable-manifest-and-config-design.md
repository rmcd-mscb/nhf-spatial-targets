# Durable manifest & config artifacts — design

**Date:** 2026-05-29
**Status:** approved (design)
**Supersedes:** the #277 approach (`backfill-aggregate-sources` + aggregate
under-report gate) and folds in #278 (consolidate-stage disk-walk). The #277
spec/plan on branch `feature/277-backfill-aggregate-sources` become *input* to
this design, not the destination.

## Problem

The pipeline is developed and run as a product *at the same time*. Provenance
and resolved-config artifacts are captured **write-time, stage-by-stage**, so
they are permanently holed wherever a stage ran before its instrumentation
existed. Co-development guarantees those holes. Two live examples, both
verified on disk 2026-05-29:

### Manifest (provenance)

- **`or-spatial-targets/manifest.json` is a fossil.** 7 source entries against
  **16** `data/aggregated/` dirs, and **0 steps** — no lineage at all. Written
  across May 14–25 while the lineage instrumentation (#245) and the entire
  `release/` subsystem were being built around it.
- **gfv2 is the same disease, milder:** 7 sources / 15 dirs, 4 steps.

(Note: `or-targets-bundle/` — a hand-assembled colleague hand-off, *not* a
codebase release product — carries no manifest, but that is not a pipeline
defect. The real codebase release path
[`payload.py::stage_fabric_child`](../../../src/nhf_spatial_targets/release/payload.py)
**already copies `manifest.json` into the staged fabric child** as a provenance
snapshot. The defect is narrower: it copies *whatever* manifest is on disk —
incomplete or fossil — and only `if manifest_src.exists()`, so an under-reported
manifest like OR's stages silently. See Pillar 3/4.)

The repair story is three partial tools with seams exactly where the holes are:

| Tool | Covers | Blind to |
|---|---|---|
| `reconcile-manifest` | datastore fetch/consolidate, **era5_land + mod16a2 only** | every other source → `no-hook` |
| `rebuild_lineage` (`release/rebuild.py`) | steps from *existing* `sources[]` | cannot add missing sources |
| `backfill-aggregate-sources` (#277, unbuilt) | `data/aggregated/` source entries + agg steps | consolidate steps (#278) |

Structural cracks the live files expose:

1. **Two skeleton definitions, no schema version.**
   [`validate.py:561`](../../../src/nhf_spatial_targets/validate.py) writes a
   6-key top-level (`created_utc`, `last_validated_utc`,
   `nhf_spatial_targets_version`, `fabric`, `sources`, `steps`);
   [`lineage.py:168`](../../../src/nhf_spatial_targets/release/lineage.py)
   `_new_manifest_skeleton()` writes only `{sources, steps}`. A lineage-first
   write can therefore produce a manifest with no `fabric` block. Nothing
   stamps a `manifest_schema_version`, so no code can ever detect "this
   manifest predates feature X" and migrate it.
2. **The publish gate is partial.** #277's gate catches aggregate under-report
   only; it punts consolidate under-report (#278) and never checks
   steps-non-empty, fabric-present, or schema-current. The OR manifest passes
   everything but the new aggregate check.
3. **Nothing guarantees a fabric has a manifest, or that a release carries one.**

### Config (resolved intent)

Comparing the two config artifacts in `or-spatial-targets/`:

| field | `config.yml` (intent) | `config.effective.yml` (autogenerated) |
|---|---|---|
| runoff period | `1979-01-01/2024-12-31` | `2000-01-01/2010-12-31` |
| aet sources | `[mod16a2, ssebop, mwbm_climgrid]` | `[mod16a2, ssebop]` — **mwbm dropped** |
| aet period | `2000.../2024` | `2000.../2010` |
| som period | `1980.../2024` | `1982-01-01/2010-12-31` |
| som normalize_period | `1980.../2024` | `null` |
| recharge period | `2000.../2013` | `2000.../2009` |
| fabric.token | `or` | `null` |

`config.effective.yml` is the **config twin of the stale manifest** — a fossil
holding the *old hardcoded TM 6-B10 windows* (`2000-2010`, `1982-2010`,
`2000-2009`) that CLAUDE.md says are no longer hardcoded. It was autogenerated
by an old `validate` and never regenerated.

- **Good:** the run path reads `config.yml` and **re-merges fresh every run**
  ([`workspace.py:95`](../../../src/nhf_spatial_targets/workspace.py)), so the
  fossil did *not* corrupt the product build.
- **Bad:** `config.effective.yml` *is* consumed as a release-lineage
  provenance input
  ([`rebuild.py:408-410`](../../../src/nhf_spatial_targets/release/rebuild.py)),
  so the stale, wrong-window config leaks into the published provenance.
- **Bad:** there is **no validation that `config.yml`'s `targets.*.sources[]`
  keys exist in the catalog** — validate only checks `variables.yml` →
  `sources.yml` ([`validate.py:404-412`](../../../src/nhf_spatial_targets/validate.py)).
  A renamed/superseded source key (merra_land→merra2, watergap22a→22d) in an
  operator config silently drops that source from a `multi_source_minmax`
  bound — a **silent under-build**, no error.

## The unifying principle

Every project artifact is **intent** (hand-authored) or **derived**
(a projection). They have opposite durability rules:

| Kind | Artifacts | Rule |
|---|---|---|
| **Intent** | `config.yml`, `catalog/` | Never auto-clobbered by development. Non-destructively upgradable (report-only). **Validated against the catalog so dangling refs fail loudly.** |
| **Derived** | `manifest.json`, `config.effective.yml`, `fabric.json` | Regenerable as a pure projection. Version-stamped. **Staleness-gated at publish.** Never hand-edited. |

The core invariant for the manifest:

> `manifest.json` = a deterministic projection of (on-disk artifacts × current
> catalog × `fabric.json`). `rebuild-manifest` is authoritative; live capture
> is a fast path the projection can always reproduce.

## Locked decisions

| # | Decision | Choice |
|---|---|---|
| A | Relation to #277/#278 | **Absorb & supersede.** One authoritative rebuild + schema version + completeness gate subsumes reconcile / rebuild / backfill / consolidate-disk-walk. |
| B | Rebuild fidelity | **Full deterministic regenerate.** Manifest = f(disk, catalog, fabric.json). Wall-clock timestamps, command lines, write-time software version are explicitly secondary. |
| C | Capture model | **Keep incremental capture** (dev fast path) **+ on-demand rebuild any time + regenerate authoritative at publish.** Adding a new dataset/variable/target must never clobber an existing manifest (auto-satisfied: the projection only changes when on-disk artifacts change; identity fields are never rewritten). |
| D | Per-fabric enforcement | **Gate-at-publish, verify-don't-mutate. No fabric registry** (a registry is new mutable state that recreates the co-dev fossil and costs idempotency). |
| E | Determinism rules (hard) | Timestamps from **file mtime only**; **never `datetime.now()` in the rebuild path**; deterministic JSON ordering (sorted source keys; steps sorted by `(kind-rank, source_key, first-output-path)`). Same disk + catalog + code → byte-identical (modulo the opt-in sha256 toggle). |
| F | Honesty | Every regenerated record tagged `provenance: "reconstructed"`; manifest stamped `manifest_schema_version` (start at `1`). |
| G | Config packaging | **One spec (this), the durability principle, covering manifest + `config.effective.yml` + catalog-key validation. Implementation plan splits into separable PRs.** |

## Pillar 1 — Schema version + one skeleton

- **One shared `_new_manifest_skeleton()`** (in `lineage.py`) carrying the full
  canonical top-level: `manifest_schema_version`, `created_utc`,
  `last_validated_utc`, `nhf_spatial_targets_version`, `fabric`, `sources`,
  `steps`. `validate._write_manifest` and the lineage writers both use it, so a
  lineage-first write can no longer produce a `fabric`-less manifest.
- `read_manifest` surfaces `manifest_schema_version` (defaulting to `0` for
  pre-version manifests).
- **`nhf-targets upgrade-manifest -d <dir>`** — report-only (mirrors the
  existing `upgrade-config` pattern): detects a manifest whose
  `manifest_schema_version` is behind current, and prints what `rebuild-manifest`
  would normalize. Never mutates on its own.
- `manifest_schema_version` is bumped **only** when the manifest *shape*
  changes (not when sources/steps content changes).

## Pillar 2 — `rebuild-manifest`: the one authoritative command

`nhf-targets rebuild-manifest -d <dir> [--compute-sha256] [--dry-run]`.

**Subsumes** `reconcile-manifest` + `rebuild_lineage` + #277
`backfill-aggregate-sources` + #278 consolidate-disk-walk behind one
**generic, catalog-keyed projection** — no per-source hook registry, which is
what kills `reconcile`'s `no-hook` gap (era5_land + mod16a2 → all sources):

- **`sources[]`** = (datastore consolidated dirs ∩ catalog) ∪ project
  `data/aggregated/` dirs. Per-key metadata (DOI, version, `access_type`,
  units) pulled from the catalog by key; file lists + periods parsed from
  on-disk filenames; size/mtime from `stat`; sha256 opt-in. Non-catalog-key
  dirs (e.g. `era5_land_sd`) get a minimal entry tagged
  `derived_variant: true` so shipped NCs are not orphaned.
- **`steps[]`** synthesized deterministically: `consolidate` (datastore NCs),
  `aggregate` (aggregated dirs), `target` (`targets/` NCs), `validate`
  (`fabric.json`).
- **Determinism** per decision E. The rebuild path imports a small
  `_now_from_mtime` helper and is lint-guarded against `datetime.now`.
- **Honesty** per decision F: records tagged `provenance: "reconstructed"`;
  the regenerated `target` steps record the *resolved* per-target config
  recovered from the target NC attrs (see Pillar 6).
- **Non-clobbering:** regenerate rewrites the derived catalog (`sources`,
  `steps`) only. `created_utc`, the `fabric` authorship block, and any
  `release` config are read-merged, never overwritten.
- Reuses the existing flock + atomic-write primitives in `lineage.py`.

`reconcile-manifest` and `backfill-aggregate-sources` become **thin shims** that
call `rebuild-manifest` (or are removed with a deprecation note); `rebuild_lineage`
is absorbed.

## Pillar 3 — Completeness gate at publish (verify, don't mutate)

Generalize #277's `_preflight_provenance_complete` into a full per-fabric
precondition in `release/publish.py`. It runs `rebuild-manifest` in
**`--dry-run`**, compares the projection to the on-disk manifest, and **refuses
if they differ** — telling the operator to run `rebuild-manifest`. Publish stays
a pure *read-local + write-remote* operation; the manifest changes only as an
explicit operator action (this is what keeps publish idempotent).

Gate assertions:

- manifest present and `manifest_schema_version` current,
- `fabric` block present,
- `steps[]` non-empty,
- `sources[]` ⊇ aggregated dirs (aggregate) **and** ⊇ consolidated datastore
  sources used (consolidate) — the #277 ∪ #278 union,
- every published target NC has a matching `target` step,
- on-disk manifest == the deterministic projection (no drift).

`--allow-incomplete-sources` is retained as the deliberate, logged override.

## Pillar 4 — Per-fabric / per-release guarantee (the Oregon issue)

"New fabric ⇒ must have a complete manifest" needs **no new bookkeeping** and no
separate bundle workstream:

- **`validate` already mints a manifest per fabric**, and the release path
  ([`payload.py::stage_fabric_child`](../../../src/nhf_spatial_targets/release/payload.py))
  **already copies it into the published child**. Each project *is* one fabric,
  so the per-fabric guarantee is the publish gate (Pillar 3) enforced
  fail-closed.
- **One-line hardening:** `stage_fabric_child` copies the manifest only
  `if manifest_src.exists()` and copies it regardless of completeness. With
  Pillar 3 in front of publish, a missing or under-reported manifest already
  fails preflight; the only change here is to make the silent
  `if exists()` skip a hard error so staging can never emit a child with no
  manifest at all.

The earlier "bundle carries no manifest" framing referred to `or-targets-bundle`,
a hand-assembled hand-off outside the pipeline — not a codebase release product,
and therefore not in scope.

Discoverability ("which fabrics exist / still need a release") is *derived* on
demand by scanning for `fabric.json`/`manifest.json` — never a maintained
registry (decision D).

## Pillar 5 — Config-artifact durability

- **`config.effective.yml` becomes a regenerable, version-stamped projection**
  of (`config.yml` × `defaults.py` × `fabric.json`), regenerated by `validate`
  and **staleness-gated at publish** with the same verify-don't-mutate
  mechanism as the manifest. Carries an `effective_config_schema_version` /
  source-config hash so a stale effective config is a *detected* inconsistency,
  not silent drift. `rebuild.py`'s release-lineage input is thereby always
  current.
- **`validate` validates `config.yml` `targets.*.sources[]` against the
  catalog** (loud `PreflightError` on a key absent from `sources.yml`, with a
  superseded-key hint pointing at `superseded_by`). Closes the silent
  under-build.
- **`upgrade-config` extended** beyond enumerated optional params to surface
  (a) whole-new-target additions absent from an existing config, and (b) "a new
  catalog source is now available for target X" hints. Still report-only.

## Pillar 6 — Config ↔ product ↔ manifest triangle

The manifest's `target` step records the **resolved per-target params actually
used** (`period`, `sources`, `normalize_period`, `ci_threshold`,
`range_method`). Because the *published* manifest is the deterministic
projection (Pillar 2), any param that must survive publish has to be
**recoverable from the target NC itself** — so this PR persists the resolved
params as target-NC global attrs (the projection then reads them back), rather
than relying on live-only manifest records that regenerate would discard.
Live capture may still record them during development, but the NC attrs are the
durable source. A stale effective config saying `2000-2010` while the
manifest/NC say `1979-2024` becomes a checkable inconsistency the publish gate
can surface.

## Pillar 7 — CLAUDE.md guardrail

New **"Manifest & config durability"** section codifying:

1. The intent-vs-derived principle and the manifest invariant.
2. The determinism rules (no `datetime.now()` in the rebuild path; mtime
   timestamps; tag `provenance: reconstructed`; deterministic JSON ordering).
3. **When you add a source/variable/target/stage:** extend the rebuild
   projection **and its test** in the same PR; bump `manifest_schema_version`
   only if the manifest *shape* changes; never write a manifest or effective
   config that bypasses the shared skeleton/projection. Modeled on the existing
   four-point "Config schema additions" checklist.
4. Every fabric gets a manifest (`validate`); every release bundle carries a
   complete one (`build`); publish is gated on completeness.

## Implementation plan (separable PRs)

1. **PR-1 — schema + single skeleton + `upgrade-manifest`** (foundational,
   small). Unify the two skeletons; add `manifest_schema_version`;
   `read_manifest` surfaces it; report-only `upgrade-manifest`.
2. **PR-2 — `rebuild-manifest`** (the generic deterministic projection).
   Absorbs reconcile / rebuild_lineage / backfill / #278. Old commands become
   shims/deprecated.
3. **PR-3 — completeness gate at publish** (verify-don't-mutate) + the
   one-line `stage_fabric_child` hardening (missing manifest → hard error
   instead of silent `if exists()` skip).
4. **PR-4 — `config.effective.yml` as a regenerable projection** + staleness
   gate + version/hash stamp.
5. **PR-5 — `config.yml` source-key validation against the catalog** +
   `upgrade-config` extension (whole-target additions + new-source hints).
6. **PR-6 — CLAUDE.md "Manifest & config durability" section** + checklist.
7. **PR-7 (optional) — config↔product↔manifest triangle** (resolved-param
   capture in `target` steps + the consistency check).

## Tests (PR-boundary requirement)

- **PR-1:** skeleton parity (validate vs lineage produce the same top-level
  shape); `manifest_schema_version` stamped; `read_manifest` defaults old
  manifests to version `0`; `upgrade-manifest` reports, never mutates.
- **PR-2** (`tests/test_rebuild_manifest.py`, new): deterministic projection
  from a synthetic datastore + `aggregated/` + `targets/` tree; **byte-identical
  on re-run** (the idempotency contract); year/period parse incl.
  `ssebop_2000_agg.nc` and `daymet_na_1980_agg.nc`; non-catalog-key dir →
  `derived_variant`; non-publishable (`watergap22d`) recorded; no
  `datetime.now()` reachable from the rebuild path (assert via a frozen-clock
  guard or import lint); concurrent flock merge.
- **PR-3:** under-report (aggregate *and* consolidate) → `PreflightError`;
  drift between on-disk manifest and projection → refusal;
  `allow_incomplete_sources` bypass; complete manifest passes;
  `stage_fabric_child` with a missing manifest → hard error (not a silent skip).
- **PR-4:** stale `config.effective.yml` detected at publish; regenerate
  matches re-merged `config.yml`; version/hash stamp present.
- **PR-5:** dangling `targets.*.sources[]` key → loud failure with
  superseded-key hint; `upgrade-config` reports new targets/sources.
- **PR-7:** resolved params land in the `target` step; config/NC/manifest
  inconsistency is surfaced.

## Smoke test (offline, real `or-spatial-targets` + gfv2, no ScienceBase)

```
nhf-targets rebuild-manifest -d <or-spatial-targets>
```
Assert the OR manifest gains all 16 aggregated sources (incl. `era5_land_sd`
as `derived_variant`) and a non-empty `steps[]` with `consolidate`/`aggregate`/
`target`/`validate` kinds; re-run is byte-identical. Then rebuild the fabric
MCF/FGDC offline (metadata-only, skip the multi-hundred-GB checksum) and confirm
the abstract source list and `processstep[]` are complete. Repeat on gfv2.

## Migration

Existing manifests (gfv2, OR) acquire `manifest_schema_version` on the next
`rebuild-manifest`, which regenerates them complete. Stale
`config.effective.yml` files are regenerated by re-running `validate` (or the
new projection). No manual editing required anywhere.

## Out of scope

- **sha256 integrity gating at publish** (never implemented; separate concern).
- **DOI minting** (sciencebasepy does not mint DOIs; out of scope here).
- **A fabric registry** (explicitly rejected, decision D — derive discoverability
  instead).
- **Re-running the heavy aggregations** under the instrumented aggregator.
- **fetch-stage raw-download republishing** (raw downloads are not published).
